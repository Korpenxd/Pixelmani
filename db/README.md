# PixelMani database (MySQL / MariaDB)

The schema for the PHP/MySQL version of PixelMani and the tooling to move the
current Supabase data into it. The live site still runs on Supabase; nothing
here is used by the Next.js app yet.

| File | Purpose |
| --- | --- |
| `schema.sql` | Creates `categories`, `photos` and `site_settings`. Run once against an empty database. |
| `seed.sql` | Ensures the `okategoriserad` fallback category exists. Idempotent. |
| `tools/export-supabase.mjs` | **Read-only** export of Supabase rows and photo files into `migration-export/`. |
| `tools/import-bundle.php` | Imports `migration-export/` into a **local** database. |
| `tools/copy-bundle-files.php` | Copies the exported photo files to `php/public/media/` (local runtime, gitignored), verified against the manifest. |
| `tools/compare-supabase-php.mjs` | **Read-only** check that the local PHP API returns the same data and file bytes as Supabase. |

The SQL stays inside a subset that behaves the same on MySQL 8.4 (local,
Laragon) and MariaDB 10.6+ (production). See the comments in `schema.sql`.

## Schema decisions

- **`okategoriserad` is a real category row**, with the label exactly
  `Okategoriserad`, created by `seed.sql`. It exists so that
  `photos.category → categories.key` can be a foreign key. In Supabase the
  key is used by photos but has no row, so the seed must run before the import.
  - **Public category lists (API and gallery filter buttons) must hide it.**
    Today's `/showcase` has no "Okategoriserad" button, and that must not change.
  - Admin and internal code use it normally: it is the upload default and the
    target when a category is deleted.
- **Foreign key `photos.category → categories.key`** uses `ON DELETE RESTRICT`
  and `ON UPDATE RESTRICT`. A category with photos cannot be deleted (the
  application moves them to `okategoriserad` first), and keys never change or
  cascade implicitly.
- **Collations** are always stated explicitly. MySQL 8's default
  `utf8mb4_0900_ai_ci` does not exist on most MariaDB versions.

  | Collation | Columns | Why |
  | --- | --- | --- |
  | `utf8mb4_bin` | category keys, `photos.category`, `storage_path`, `thumb_path`, `site_settings` | Exact comparison: `a` ≠ `å`, `portratt` ≠ `porträtt` |
  | `ascii_bin` | UUID `id` columns | Exact and compact |
  | `utf8mb4_swedish_ci` | `categories.label` | Swedish alphabetical order: Å, Ä, Ö after Z |
  | `utf8mb4_unicode_ci` | photo `name`, `title`, `location` | General human-readable text |
- **`photos.storage_path` is UNIQUE.** Every stored file belongs to exactly
  one photo. The importer also rejects a bundle with duplicate paths before
  touching the database.
- **Timestamps** are `DATETIME(6)` in UTC. Microseconds are kept because
  photos uploaded together differ only by fractions of a second, and the
  gallery is ordered by `created_at`.
- **UUIDs** are generated by the application, never by the database.

## Configuration

Copy `.env.loopia.example` (repo root) to `.env.loopia.local` and fill in your
local values. `.env.loopia.local` is gitignored. Variables set in the shell
override the file.

```
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=pixelmani_local
DB_USER=<local user>
DB_PASSWORD=<local password>
DB_CHARSET=utf8mb4
```

## Creating the local database

### Laragon / MySQL CLI

Start MySQL in Laragon, then from the repo root (Laragon's terminal has
`mysql` on the PATH; otherwise use `C:\laragon\bin\mysql\mysql-8.4.3-winx64\bin\mysql.exe`):

```bash
mysql -h127.0.0.1 -u<user> -p -e "CREATE DATABASE pixelmani_local CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
mysql -h127.0.0.1 -u<user> -p --default-character-set=utf8mb4 pixelmani_local < db/schema.sql
mysql -h127.0.0.1 -u<user> -p --default-character-set=utf8mb4 pixelmani_local < db/seed.sql
```

Always pass `--default-character-set=utf8mb4` when feeding files to the CLI,
otherwise Swedish characters in the SQL can be mis-read on Windows.

### phpMyAdmin / Adminer

1. Create a database named `pixelmani_local` with collation `utf8mb4_unicode_ci`.
2. Select it, open **Import** (phpMyAdmin) or **SQL command → File upload** (Adminer).
3. Import `db/schema.sql`, then `db/seed.sql`. Choose `utf8mb4` as the file charset.

To start over, drop and recreate the database. `schema.sql` deliberately fails
if the tables already exist.

## Migrating the Supabase data

### 1. Export (read-only)

```bash
node db/tools/export-supabase.mjs
```

- Uses `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from the
  environment or `.env.local`, which is the same public access every visitor has.
- Only issues HTTP `GET` requests, and only to:
  - `/rest/v1/photos`, `/rest/v1/categories` and `/rest/v1/site_settings` (rows)
  - `/storage/v1/object/public/photos/<storage_path>` (files)

  Any other request is refused in code before it is sent.
- Writes `migration-export/` (gitignored: it contains production data):

```
migration-export/
  manifest.json            export time, row counts, checksums, file list, missing files
  metadata/photos.json
  metadata/categories.json
  metadata/site_settings.json
  files/uploads/...        byte-for-byte copies, original names and paths
  files/hero/...
```

- Refuses to overwrite an existing bundle unless given `--overwrite`.
- Exits with code 2 if any referenced file is missing or has an unsafe path.
- **Stays GET-only by design.** It does not list the bucket, because listing
  requires a POST. Files in the bucket that no row refers to are therefore
  outside the integrity check. That is an accepted limitation: only files the
  database points at are migrated.

### 2. Import (local database only)

```bash
php db/tools/import-bundle.php --dry-run
php db/tools/import-bundle.php
```

Use Laragon's PHP (`C:\laragon\bin\php\php-8.3.*\php.exe`) if `php` is not on the PATH.

- Refuses any `DB_HOST` other than `127.0.0.1`, `localhost` or `::1`.
- Verifies the checksums in `manifest.json` before reading any rows.
- Keeps ids, category keys, `storage_path`, `created_at` (converted to UTC,
  microseconds kept) and site settings exactly as exported. Empty strings in
  nullable text columns become `NULL`.
- Runs in a single transaction and verifies the result before committing.
  `--dry-run` rolls it back.
- Re-running is safe: rows that are already identical are skipped. If a row
  differs, the import aborts unless `--replace` is given. Rows that exist only
  in the database are reported and never deleted.
- Aborts if a photo refers to a category that does not exist, or if two
  photos share a `storage_path`. **Run `seed.sql` first**: the current
  Supabase data has photos in `okategoriserad` but no `okategoriserad` row in
  `categories`.
- Imports metadata only. Photo files stay in `migration-export/files/` until
  the upload/storage phase decides where they live.

### Verifying

```sql
SELECT (SELECT COUNT(*) FROM photos) AS photos,
       (SELECT COUNT(*) FROM categories) AS categories,
       (SELECT COUNT(*) FROM site_settings) AS settings;

SELECT id, created_at FROM photos ORDER BY created_at DESC;   -- compare with manifest.json ordering
SELECT * FROM site_settings WHERE `key` = 'hero_image_path';
```
